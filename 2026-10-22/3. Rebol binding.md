## The one idea

A word is two things glued together: a **spelling** and a **binding**, which is a pointer to a context (a table of spelling → value slots).

```
word  =  ( spelling , pointer-to-context )
```

Everything about binding follows from this. The environment is not something `do` carries around. It is stored inside each word.

## Example 1: one word, one context

```rebol
x: 10
blk: [x]
do blk          ; == 10
```

When this source was loaded, every word was bound to the global context. The `x` in `blk` is a separate word value from the `x:` before it, but both have the same spelling and the same pointer to the global context. So `do` follows the pointer, finds the slot `x`, and gets 10.

```
x:  (x, ●)──┐
[x] (x, ●)──┼──► global context:  x = 10
```

## Example 2: same spelling, two contexts

```rebol
x: 10
o: make object! [x: 20]
blk: [x]

do blk                  ; == 10
do bind blk o           ; == 20
```

`make object!` creates a new context with a slot `x`. `bind blk o` walks `blk` and, for each word whose spelling exists in `o`, rewrites that word's pointer to `o`:

```
before:  blk: [ (x, global) ]      → global.x = 10
after:   blk: [ (x, o)      ]      → o.x      = 20
```

The spelling is unchanged. Only the pointer moved. This is the whole mechanism.

## Three gotchas

**`bind` mutates the block.** It rewrites the words in place and returns the same block:

```rebol
do bind blk o           ; == 20
do blk                  ; == 20   (blk itself was changed)
```

To avoid this, bind a copy: `do bind copy blk o`. (`copy` is shallow, so words in nested blocks still get rebound. Use `copy/deep` if that matters.)

**Only matching spellings are rebound.** If `o` has `x` but not `y`, then in `bind [x y] o` the `y` keeps its old binding. Contexts don't extend themselves.

**Unbound words exist.** Words made at runtime, like `to-word "zzz"`, have no context. Evaluating one is an error.

## Working with a word directly

Since the binding is in the word, you can pick a word out of a context and use it on its own:

```rebol
w: in o 'x      ; the word x, bound to o
get w           ; == 20
set w 99
o/x             ; == 99
```

`o/x` is a path doing roughly the same thing.

## Example 3: functions are just more contexts

```rebol
x: 1
f: func [x] [x * 2]
f 5             ; == 10
x               ; == 1
```

`func` makes a context for its parameters and binds the body block to it. The `x` inside the body points at the function's context, not the global one, so the global `x` is unaffected. A function definition is "make a context, bind the body to it". `use` exposes the same idea directly:

```rebol
use [t] [t: 5  t * 2]    ; == 10, and t doesn't leak
```

Objects, functions, and `use` all create a context and bind a block to it.

## How this differs from Lisp

In Lisp, a quoted `'(x)` contains a bare symbol. When you `eval` it, the meaning of `x` comes from the environment in effect at the `eval` call (an explicit argument in Scheme, dynamic or lexical context elsewhere). The data has no idea where it came from.

In Rebol, `do` takes no environment. The block's words already know where to look. This has two consequences:

- A block can be built in one place, passed around, and `do`ne somewhere else, and its words still refer to the variables they were bound to. That is lexical-like behavior without needing the scope tree at eval time.
- Changing meaning means rewriting the words with `bind`, rather than passing a different environment to `eval`.

## Connection to arity

This ties back to your earlier point. When `do` reaches a word, it follows that word's pointer, gets the value, and only then knows whether it's a function and how many arguments to consume. So the pointer in the word decides the call structure. Rebind `g` to a different context where `g` has a different arity, and the same block parses into a different tree.

Caveat: this is the classic Rebol 2/R3 model. Ren-C reworked binding substantially (it adds relative and virtual binding to fix problems with functions and nested blocks), so details like what `make object!` and `bind` do to nested blocks differ there.
