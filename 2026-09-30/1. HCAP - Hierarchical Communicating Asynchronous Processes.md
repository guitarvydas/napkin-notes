The problem with CSP is that the processes are synchronous.
Synchronous is the exact opposite of asynchronous.
It is very hard it is impossible to express asynchronous processes using asynchronous notation.
We've been pushing on CSP like processes for some 50 years and have modified the hardware to get sort of parallelism where CPUs have private L0 cashes L one cashes, but as soon as those see views try to access memory beyond L1 the hardware synchronizes them with other processes in the system.
The only reasonable way to deal with asynchronous processes is to synchronize them in someway using some sort of protocol.
If that protocol is ultra generalized it is taken out of the hands of the software architect and cannot be optimize on per project basis this also leads to accidental complexity adding lots and lots of code to try and keep things running within the L1 cash.
A more reasonable and more simple way of doing this is to allow the architect to choose when to synchronize and this is done by simple message passing we see this kind of thing in the Internet and message passing systems in true asynchronous message passing systems.

The synchronous straitjacket also hinders thinking about hierarchy architecture software architecture.
It is much easier to express a hierarchical architecture using message passing between notes that are not coupled via call return and function calling.
This is why using current programming languages makes it appear to be very difficult to write an ethernet stack yet using something like state charts makes it quite easy.
