# The Synchronous Straitjacket

## The problem with CSP

The problem with CSP is that the processes are synchronous. Synchronous is the exact opposite of asynchronous. It is very hard, in fact impossible, to express asynchronous processes using synchronous notation.

We've been pushing on CSP-like processes for some 50 years. We have modified the hardware to get a sort of parallelism: CPUs have private L0 and L1 caches. But as soon as those CPUs try to access memory beyond L1, the hardware synchronizes them with the other processes in the system.

## Synchronization is unavoidable, but who controls it?

The only reasonable way to deal with asynchronous processes is to synchronize them in some way, using some sort of protocol.

If that protocol is ultra-generalized, it is taken out of the hands of the software architect. It cannot be optimized on a per-project basis. This also leads to accidental complexity: lots and lots of code added to try to keep things running within the L1 cache.

A more reasonable and simpler way is to let the architect choose when to synchronize. This is done with simple message passing. We see this kind of thing on the Internet and in true asynchronous message-passing systems.

## Hierarchy

The synchronous straitjacket also hinders thinking about hierarchical software architecture. It is much easier to express a hierarchical architecture using message passing between nodes that are not coupled via call/return and function calling.

This is why, using current programming languages, it appears to be very difficult to write an Ethernet stack, yet using something like statecharts it is quite easy.

We saw someone building an Ethernet stack in the language C. After six months he was still testing it. We rebuilt the same stack in only two days, using a different mindset: the mindset of state machines.

## Parts Based Programming

Lately I've been experimenting with a system I call Parts Based Programming (PBP), formally called 0D. It uses simple Python and first-class functions to create asynchronous processes. The nodes are functional, but can only communicate with the outside world through input and output queues.

Creating simple hierarchies this way is natural, and the code inside each node remains fairly simple and easy to understand. You can dig into a node as deeply as you want to discover details. You can also simply get a view of the bigger picture by looking at the upper layers, without bothering to dig down.
