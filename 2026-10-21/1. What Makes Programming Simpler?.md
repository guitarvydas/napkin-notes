# What Makes Programming Simpler?
2026-10-21

My favourite definition of "simplicity" is "the lack of nuance".

## What Makes Programming Simpler?
- garbage collection\
- heterogenous lists & collections\
- JIT typing (aka dynamic typing)\
- freedom to choose underlying paradigms, i.e. Forth[^1], Prolog[^1], functional, string-only manipulation...\
- drawings and diagrams\
- explicit expression of state-based control flow in a non-textual manner, e.g. Statecharts\
- explicit expression of flowcharts in a non-textual manner, currently I think that Drakon is a better approach to flowcharting\
- macros[^2] and code-that-writes-code\
- REPLs (Read Eval Print Loops)[^3]\
- a restricted set of types, e.g. Sector Lisp has only two major types - lists and atoms.\

## What Makes Programming More Complicated?
- nuance
- AOT typing (Ahead of Time, aka compilation)
	- AOT typing is useful for program analysis, but I'm not convinced that it is helpful for program creation, e.g. many great programs were created without AOT typing, e.g. UNIX[^4], Turbo Pascal, VisiCalc\
- the view that everything can be understood if expressed as a functional computation\
- tight coupling hidden by underlying hardware (e.g. CALL/RETURN)\
- formalization
	- formalization is difficult and slows productivity down and tends to restrict inventiveness\
	- some, rightly, feel that formalization is necessary, but formalization should not stand in the way (a roadblock) of creating software, as it currently does\
- appeasing the type checker and warping languages to suit the inability of type checking algorithms to handle all actual use-cases\
- thinking that K&R C and ANSI C are the same language\
- thinking that C is "close to the hardware" (only true for PDP CPU architectures)
	- K&R C was only a helper for generating PDP assembler (literally, `cc` would convert C source text into assembler source text, then another program (`as`) would convert the assembler text to binary)\

[^1]: Note that Forth and Prolog (and probably other languages) do not adhere to common calling conventions, like that of `cdecl`, `stdcall`, etc. Languages that adhere to these calling conventions can only simulate concepts like those in Forth, Prolog, etc. Just the phrase "calling convention" means that one is using the function-calling paradigm. Prolog, for example, does not implement functions, even though the syntax (textual) might look like functions and function calls. Modern languages seem to be wedded to the concept of using functions for writing programs, although this is not necessary. I believe that the overuse of the function-calling paradigm restricts the thought process and reduces the ability to solve problems.
[^2]: Lisp macros are vastly different from the stunted thing called "macros" in something like the C language. In C, macros are written in a limited language which doesn't resemble C. In Lisp, a macro can use all of the features of the Lisp language. Macros are evaluated inside of the compiler and affect the compilation process.
[^3]: Lisp-like REPLs allow the use of the full Lisp language at the REPL command line and allow redefinition of procedures and functions. I believe that supporting such full access is vital to flexibility and simplicity in creating software. I believe that programming consists of two phases (Design Engineering, Production Engineering)
[^4]: Contrary to the false advertising that I was fed for decades, I recently discovered that UNIX V1 was originally written in assembler. A K&R C version of UNIX only came later (V4). It might be worth trying to figure out how assembler contributed to freedom of thought and invention. Formalization of these concepts only came later, after the concepts had been invented.
