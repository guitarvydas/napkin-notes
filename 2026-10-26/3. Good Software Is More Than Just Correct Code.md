Good Software Is More Than Just Correct Code

2026-10-26

# Separation

I liken software to other professions, say something like Structural Engineering.

## Software Architecture

- thinking deeply about requirements
- thinking deeply about the desire for fit within a given environment
- rough-in, sketch of general design

## Software Engineering

- thinking deeply about details
- can the design be accomplished or do we need to push back on the SW Architects?
- what's missing, what concrete parts are needed for a self-consistent design of SW Architects' ideas?
- create blueprints for implementation and/or create MVI (Minimum Viable Implementation - reference implementation, reference semantics - as opposed to MVP (Minimum Viable Product, which skimps on design in lieu of coding))

## Coding - Software Implementation

- building what's specified in the blueprints
- or, pushing back and getting Engineers to make changes and to sign off on the changes
- if the software breaks because coders made egregious changes, it's the coders' fault
- if the software breaks because the Engineering was faulty, it's the SW Engineers' fault
- if the software breaks or doesn't satisfy because of other reasons, it's the SW Architects' fault

## Software Analysis

- proving traceability between Engineering blueprints and coders' product
- proving inner consistency of code, e.g. via detailed type checking

## Software Production Engineering

- optimization of a working design to make it "more efficient" along some dimension

## QA - Quality Assurance

- paid to black-box test the design and the code
- being as adversarial as possible, finding loopholes that SW Engineers and SW Architects didn't think of
- figure out what needs to change before customers complain or before they make suggestions for design improvement (usually slowly)

## Test Engineering

-  examine design and code for "testability" and push back at appropriate levels
- making the product testable

## other

- I've probably missed many important aspects

# Accountability

Real professions split work along these lines. SW Engineers should not write code, only think about what code needs to exist and create blueprints. 

It is my understanding that "Architecture" and "Engineering" are legal terms and that such professionals must sign or stamp their work and take legal responsibility, e.g. they can be sued in court.

In a cottage industry, a single person (or a single group) is responsible for doing all of the above, often with milquetoast results, poor reproducibility,  poor overall design vs. implementation balance, reliance on customers' suggestions, e.g. through use of continuous deployment instead of striving for zero defects in the field (design defects and code defects)
