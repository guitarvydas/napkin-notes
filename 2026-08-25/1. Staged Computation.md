> the fact that parse allows actions during parsing defied "computation". Is this a form of staged computation?

Short answer: not quite — what PARSE is doing is closer to **syntax-directed semantic actions** (the yacc/attribute-grammar/parser-combinator idiom) than to staged computation in the technical sense. But there's a related place in Rebol where genuine staging _does_ show up, and it's worth separating the two.

## What "staged computation" actually means

In the PL-theory sense (MetaML, MetaOCaml, partial evaluation), staging means a **temporal/phase separation**: stage 1 computes a _program_ (a code value) as its output; that program is a distinct artifact — inspectable, cacheable, specializable — that only gets _executed_ in a later, separate stage 2. The classic payoff is performance: stage 1 does the generic/slow work once, producing a specialized residual program that stage 2 runs many times without re-paying stage 1's cost. The hallmark is a **quote/splice boundary** — `<<...>>`/`~` or `Code[T]` types — marking "this is a program, not yet a value."

## What PARSE's embedded actions actually do

```rebol
parse "(416)555-1234" [
    "(" copy area 3 digits ")"
    copy exch 3 digits "-"
    copy line 4 digits
    (print rejoin [area "-" exch "-" line])
]
```

This is **one pass**. There's no moment where a residual program is produced and handed off to a later, separate execution phase — recognition and action are interleaved in the same walk over the same data, right now. This is exactly the pattern in:

- yacc/bison `{ ... }` reduce actions,
- attribute grammars (each production carries a semantic action),
- monadic parser combinators' `.map`/`>>=` on a successful parse.

None of those are normally called "staged" — they're called syntax-directed translation. The action fires _during_ recognition, not _after_ recognition has finished and produced something to run separately.

## Where staging genuinely shows up nearby

The more interesting staging-adjacent fact about Rebol isn't the action-embedding — it's that **the rule block is just an ordinary value**. Nothing stops you from building it programmatically (via `compose`, `reduce`, string/block manipulation) _before_ ever calling `parse` on it:

```rebol
rule: compose [3 digits (either strict? ["-"] [opt "-"]) 3 digits]
parse input rule
```

_That_ is a real two-phase split: phase 1 constructs a data value (a grammar), phase 2 (a separate call to `parse`) interprets it. This is much closer to what Lisp macros do — and it leads to a slightly counterintuitive conclusion worth filing away for your comparison: **Lisp macros are more genuinely "staged" than PARSE's embedded actions are.** Macroexpansion is a hard, distinct phase (compile-time) that produces a new program, which is then compiled/run in a separate phase (run-time) — a true quote/splice boundary. PARSE's `(...)` actions have no such boundary; they're just interleaved evaluation.

If you want a real example of compile-time-vs-run-time staging in the "adjacent languages" list from your brief, **Forth** is the sharper analogy, not PARSE: `IMMEDIATE` words execute _during compilation_ of the surrounding definition and can emit different code depending on what they see — a genuine two-stage (compile-time-generates, run-time-executes) split, much closer to MetaML-style staging than anything PARSE does.

**So, to name it precisely for your notes:** PARSE's embedded actions = syntax-directed evaluation (single-pass, interleaved). Rule blocks as first-class, programmatically-constructible data = the homoiconic "code as data" property that _enables_ staging, same mechanism Lisp macros exploit — but PARSE itself doesn't use that mechanism to stage anything; it just interprets whatever block it's handed, once, inline.
