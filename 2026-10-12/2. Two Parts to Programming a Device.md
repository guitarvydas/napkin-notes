# Two Parts to Programming a Device

## Two Aspects of Programming

There are (at least) 2 aspects to programming a device:

1. Design Engineering
2. Production Engineering

Most of our AOT (Ahead of Time, statically, strongly typed) programming languages are geared for Production Engineering.

We tend to solve both aspects using the same, single kind of programming language, one geared for Production Engineering.

## Design Languages Are Shunned

We have been taught that languages that support Design Engineering should be shunned as not being sufficiently detailed. Such languages tend to be dynamically typed, e.g. Javascript, Python, Lisp, etc.

Meanwhile, we have tools that support poor design, e.g. "CD" (the CD in CI/CD). We expect paying customers to (slowly) give us hints about how to improve designs.

## Premature Optimization of Game Logic

When we need to create a hot, fast graphics driver, we use a systems programming language (like C++, etc.).

Due to the way our current workflow is, we end up using the very same language to code up higher level constructs like game logic, which doesn't need the same level of optimization. In essence, the game logic becomes prematurely optimized, with the result that game logic design suffers from thinking at too low a level.

## Why Design Suffers

- Design is hard to address and hard to quantify. Production engineering is much easier to quantify.
- AOT languages encourage Waterfall design and encourage deferring design to future feedback.
- Correct code does not imply good design, or at least, sufficient design.

### Designs Need Iteration

We need to iterate and test Designs, and to "go back to the drawing board". This means we need the ability to wipe the slate clean, discard all existing code, and re-code.

If one has spent lots of time appeasing a type checker, one is reluctant to discard code. One tends to tweak what they've already got, regardless of whether it is fundamentally flawed.

Anecdote: we waited two years for an IDE to be built. When we finally saw it, we immediately asked to change the layout. The programmer told us "no", because it would involve too much rework of the code that was painstakingly created over the past few years.

## MVI vs. MVP

MVI is different from MVP.

### MVP

MVP (minimum viable product) skimps on Design. It reduces the Design to bits that can be implemented, using current tools, in short (say 2 week) chunks.

### MVI

MVI (minimum viable implementation) creates an engineering version of a full product, while skimping on optimization and production engineering issues.

MVI is iterative and stops only when the design is deemed full enough to be useful. Once a design variant is chosen and settled on, production engineering can commence, either to implement the whole thing or to release it in chunks. There is no expectation of upgrading the actual design.

### Provenance

We should want (but don't have, today) a way to track provenance from the original Design to the actual Production version.

## What Do We Need?

### Languages for Design

We already have some languages that use dynamic typing and REPLs, like Lisp and Smalltalk.

### A Mapping From Design to Production

We need a way to map constructs in design languages to constructs in production engineering languages.

What does it mean to have a list of heterogeneous (differently typed) objects, and how can that be automatically mapped to AOT languages?

Currently, we do this manually, by insisting on programming rules, like not allowing the use of heterogeneous objects.

### Hardware Data Types

There are only 2 fundamental data types in hardware:

- byte
- pointer to byte

This is not actually accurate. It depends on CPU architecture, and sometimes signed bytes and 16-bit integers are supported.

The question is how to map abstract types, like user-defined data structures, objects, etc., to hardware data types.

Compilers are expected to do this, but don't currently succeed in mapping coarse-grained Objects to hardware types without wasting memory. For example, we often need to build separate data structures and functions for each type. Compilers can only optimize at a low level, not at a semantic level.

Does the relatively recent invention of union types give us a way to create heterogeneous data structures that can be used to map (dynamically typed) Design issues to (statically typed) Production issues?
