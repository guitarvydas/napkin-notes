# Two Parts to Programming a Device
There are (at least) 2 aspects to programming a device
1. Design Engineering
2. Production Engineering

Most of our AOT (Ahead of Time, statically, strongly typed) programming languages are geared for Production Engineering.

We tend to solve both aspects of programming using the same, single kind of programming languages - geared for Production Engineering. 

We have been taught that languages that support Design Engineering should be shunned as not being sufficiently detailed. Such languages are dynamically typed, e.g. Javascript, Python, Lisp, etc. and, we have tools that support poor design, e.g. "CD" (the CD in CI/CD). We expect paying customers to (slowly) give us hints about how to improve designs.

For example, when we need to create a hot, fast graphics driver, we use specific systems programming languages (like C++, etc.). Due to the way our workflow works, we end up using the very same language to code up higher level constructs like game logic, which doesn't need the same level of optimization. In essence, the game logic becomes prematurely optimized with the result that game logic design suffers from thinking at too low a level.

- hard to address design - hard to quantify design, much easier to quantify production engineering
- AOT languages encourage Waterfall design and encourage deferring design to future feedback
- correct code does not imply good design, or at least, sufficient design
- need to iterate and test Designs and to "go back to the drawing board"
	- we need the ability to wipe the slate clean, discard all existing code and to re-code
	- if one has spent lots of time appeasing a type checker, one is reluctant to discard code and tends to tweak what they've already got, regardless if it is fundamentally flawed
		- anecdote: we waited two years for an IDE to be built, then when we finally saw it, we immediately asked to change the layout - the programmer told us "no" because it would involve too much rework of the code that was painstakingly created over the past few years.

## MVI vs. MVP
MVI is different from MVP. 

MVP (minimum viable product) skimps on Design and reduces the Design to bits that can be implemented, using current tools, in short (say 2 week) chunks. 

MVI (minimum viable implementation) creates and engineering version of a full product, while skimping on optimization and production engineering issues. 

MVI is iterative and stops only when the design is deemed full enough to be useful. Once a design variant is chosen and settled-on, production engineering can commence to either implement the whole thing or to release it in chunks. There is no expectation of upgrading the actual design.

We should want (but don't have, today) a way to track provenance from the original Design to the actual Production version.

## What Do We Need?
- languages for Design
	- we already have some languages that use dynamic typing and REPLs, like Lisp, Smalltalk, 
- a way to map constructs in design languages to constructs in production engineering languages
	- what does it mean to have a list of heterogenous (differently typed) objects and how can that be automatically mapped to AOT languages?
	- currently, we do this manually, by insisting on programming rules, like not allowing the use of heterogenous objects
- there are only 2 fundamental data types in hardware
	- byte
	- pointer to byte
	- (not actually accurate - depends on CPU architecture, sometimes signed bytes and 16-bit integers are supported)
	- how to map abstract types, like user-defined data structures, objects, etc. to hardware data types 
		- compilers are expected to do this, but don't currently succeed in mapping rough-grained Objects to hardware types without wasting memory (e.g. we often need to build separate data structures and functions for each type), compilers can only optimize at a low level but not at a semantic level
		- does the relatively recent invention of union types give us a way to create heterogenous data structures that can be used to map (dynamically typed) Design issues to (statically typed) Production issues?
