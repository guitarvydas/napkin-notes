# Three Tiers of Programming a Device

## Three Tiers, Not One

There are (at least) three tiers to programming a device:

1. Architecture
2. Engineering
3. Production

Architecture decides what the thing is: its overall form, its parts, and how it should feel to the people who use it. This is the clay modeler's work.

Engineering checks that the architecture holds together. It makes sure every piece has been designed in, that the pieces can be affixed to one another in some manner, and that the i's are dotted and the t's crossed. It does not choose the cheapest glue or fastener for every situation.

Production takes a settled design and makes it fast, small, cheap, and shippable. This is the stamping die and the fastener catalogue. It is a different kind of engineering, concerned with optimizing along particular dimensions. Beneath it sits the plain act of implementation, which is not engineering at all. It is carrying out a plan that has already been made.

Architecture and Engineering together are what I call Design. Production is the other half.

Most of our AOT (Ahead of Time, statically, strongly typed) programming languages are geared for Production. They are excellent at catching mistakes in the details and generating tight machine code.

## The Cottage Industry Mentality

Yet we use the same, single kind of programming language for all of it. Architecture, engineering, and implementation are conflated, and one person, in one language, in one sitting, does all three. This is the cottage industry. The village cabinetmaker sketches the chair, works out the joinery, selects the wood, and cuts it, all at one bench with one set of tools. For one chair this works well. It does not scale to a skyscraper, a car, or a game engine.

Industries that grew out of the cottage stage did so by finding clean separations between the tiers, and a notation for each one. The architect's drawings are not the engineer's calculations, and neither is the machinist's tooling spec. Each tier has its own notation, tuned to the questions that tier asks, and each hands something well-defined to the next.

Programming has not made this move. We have one notation, shaped by the needs of the lowest tier, and we ask it to carry the thinking of the other two. To leave the cottage, we need to find the clean separations between architecture, engineering, and production, and a notation for each.

## Design Languages Are Shunned

We have been taught that languages that support Design should be shunned as "not sufficiently detailed." These are the dynamically typed languages, e.g. Javascript, Python, Lisp. The usual complaint is that they let you get away with too much, as if an architect's sketchbook were faulty for lacking a tolerance table.

Meanwhile, we have built tools that support poor design. Consider the "CD" in CI/CD. The pipeline ships quickly and often, and the design is expected to improve afterwards. We expect paying customers to (slowly) give us hints about how to improve the design. In effect, the customers become the design review team, and they never signed up for the job.

## Premature Optimization of Game Logic

When we need to create a hot, fast graphics driver, we use a systems programming language (like C++, etc.). That is a sensible choice, since the driver sits in the tightest loop of the program and every cycle counts. It is Production work, and it deserves a Production language.

But because of the way our workflow works, we end up using the very same language to code up the higher-level constructs, like game logic, which doesn't need the same level of optimization. Whether a dragon decides to attack or flee is not a decision that has to be made in nanoseconds. In essence, the game logic becomes prematurely optimized, and its design suffers from thinking at too low a level. We end up designing the dragon's personality in the vocabulary of memory layouts and register pressure. The architecture and the engineering of the game logic never get a tier of their own, so they are done, if at all, in the dialect of the tier below.

## Why Design Suffers

Several forces conspire against Design:

- Design is hard to address and hard to quantify. Production is much easier to quantify. We can measure frames per second, memory footprint, and test coverage. "Is this a good design?" has no such gauge, and what we can't measure tends to get neglected.
- AOT languages encourage Waterfall design and encourage deferring design to future feedback. The language demands that types be nailed down early, so the Design hardens before it has been tried.
- Correct code does not imply good design, or at least, sufficient design. A program can be flawless and still be the wrong program, like a perfectly constructed bridge to the wrong side of the river.

### Designs Need Iteration

We need to iterate and test Designs, and to "go back to the drawing board." That means we need the ability to wipe the slate clean, discard all existing code, and re-code. A painter who sees that a composition is wrong paints over the canvas, and nobody calls that waste.

But if one has spent lots of time appeasing a type checker, one becomes reluctant to discard code. Each hard-won type signature is a small sunk cost, and together they make a large one. So one tends to tweak what they've already got, regardless of whether it is fundamentally flawed. The code stops being a draft and becomes a monument.

An anecdote: we waited two years for an IDE to be built. When we finally saw it, we immediately asked to change the layout. The programmer told us "no," because it would involve too much rework of the code that was painstakingly created over the past few years. The first time the users could see the design was too late to change it.

## MVI vs. MVP

MVI is different from MVP.

### MVP

MVP (minimum viable product) skimps on Design. Design is adversely altered by the MVP approach, because the toolset ends up deciding what gets designed in the first place.

It works like a tailor who owns only one pair of scissors and one bolt of cloth. Every suit he makes ends up with the same cut, and he calls this "what the customer needs." We design only what the current toolset provides for. We bend the Design to fit the implementation tools (usually Production tools), instead of thinking about the Design first and then choosing tools that let us implement it.

Suppose the Design calls for a list of differently typed things, say a game's inventory holding swords, potions, and keys. If the only tool at hand is a statically typed systems language that makes heterogeneous lists awkward, the Design quietly changes. The inventory becomes three separate lists, or a single "Item" type with a pile of optional fields. Nobody decided that this was better design. It was simply easier to implement.

The short sprint adds to this. A sprint of, say, two weeks rewards whatever fits in a two-week box, so the Design is trimmed into bits of that size. Pieces that don't fit are cut or deferred, much like a sculptor who can only carve what fits in the block he happened to buy.

### MVI

MVI (minimum viable implementation) creates an engineering version of a full product, while skimping on optimization and production issues. Where MVP builds a small piece of the product, MVI builds a rough version of the whole product. It is the full-scale clay model, as opposed to one finished car door.

The clay modeler works at the level of architecture, shaping the whole form and deciding how it should look and feel. The stamping die sits at the opposite end, a very low-level concern about how to make thousands of identical panels cheaply. The engineer works in between. At this stage, engineering consists of thinking about the design and figuring out which i's need to be dotted and which t's need to be crossed. The engineer checks that all of the pieces have been designed in and that each can be affixed in some manner. The engineer does not need to decide which glue or hardware fastener is cheapest in every situation, or spend brain bandwidth rearranging the bits of the engineering to optimize along certain dimensions.

MVI is iterative and stops only when the design is deemed full enough to be useful. Once a design variant is chosen and settled on, Production can commence, either to implement the whole thing or to release it in chunks. There is no expectation of upgrading the actual design. The first two tiers end, and Production inherits a design that has already been tried and found good.

## Provenance Across the Tiers

We should want (but don't have, today) a way to track provenance from the original Architecture, through the Engineering, to the actual Production version. When a production decision departs from the design, we should be able to see where and why. Today the thread is cut at each handoff, and the production code can't tell us which parts are essential to the design and which are accidents of the toolset.

## What Do We Need?

### A Notation for Each Tier

Each tier needs its own notation, shaped by the questions that tier asks. We already have some languages that use dynamic typing and REPLs, like Lisp and Smalltalk. They let you ask a question of the program while it runs, and they make throwing code away cheap, which is exactly what the upper two tiers need. Production already has its languages: the AOT languages we have today.

The work might need to be split into more than three tiers. This is where I would start.

### Mappings Between the Tiers

We need a way to map constructs in the upper tiers to constructs in Production languages.

What does it mean to have a list of heterogeneous (differently typed) objects, and how can that be automatically mapped to AOT languages? Currently, we do this manually, by insisting on programming rules, like not allowing the use of heterogeneous objects. The rule is sensible on its face, but it filters the Design before the Design has been judged on its merits, which is the MVP problem again.

### Hardware Data Types

At the bottom, there are only two fundamental data types in hardware:

- byte
- pointer to byte

Hardware is a vast warehouse of identical boxes, each with an address painted on the front. Everything else is a convention about how to read the contents of the boxes.

This is not strictly accurate. It depends on CPU architecture, and some CPUs support signed bytes and 16-bit integers. But the picture is close enough to pose the question: how do we map abstract types, like user-defined data structures and objects, onto those boxes?

Compilers are expected to do this, but they don't currently succeed in mapping coarse-grained Objects to hardware types without wasting memory. For example, we often need to build separate data structures and functions for each type. Compilers can optimize at a low level, like shuffling registers and eliminating dead stores, but not at a semantic level. A compiler can tidy the boxes, yet it has no idea what the boxes mean.

### A Possible Bridge: Union Types?

Does the relatively recent invention of union types give us a way to create heterogeneous data structures that can be used to map (dynamically typed) Design issues to (statically typed) Production issues? If so, the inventory of swords, potions, and keys could live in the Design as one natural list, and be mapped into a production-ready layout without anyone having to bend the Design to fit.

I don't know the answer, but it seems a question worth pursuing.
