# What Is Simplicity?
"lack of nuance"
# Examples of Simplicity
- UNIX
	- normalizes all APIs to devices, files, etc. to be one normalized kind - "files" and file descriptors
- Forth Haiku
	- small, simple notation maps to complicated GLSL code (approx. 2 lines to 100 lines)
- Forth
- Lisp 1.5
- Jos'h's command line arg parser, using arg reversal
- BNF as a way of specifying string matching (and eBNF, etc.)
- CPU opcodes instead of rats' nests of electronics
- Feynman diagrams
	- instead of just more functional equations
- K&R C vs. ANSI C
	- K&R C defines all routines to be "functions"
	- K&RC invented a simple type-checking model that covered a lot of cases, but not all cases - it was "just enough" to build systems software
- Prolog and relational programming
	- allows more concise expression of relationships, at cost of run-time speed (needs more CPU cycles)
- childrens' LEGO blocks
	- only one type for interconnection of blocks - a round peg of fixed dimensions
	- no tight coupling between blocks
	- blocks are interchangeable
- multi-stage computation
	- each stage does one thing and does it well
	- allows programmers to concentrate on only one thing at a time (leading to deeper solutions instead of wasting time on workarounds)
# Examples of Anti-Simplicity
- overuse of the functional paradigm
	- forcing all problems to fit one model - causes workarounds and unnecessary nuance when fitting a problem to the single model
	- the strive to use CPUs to automate mathematics has leaked, heavily, into programming practice, e.g. most programming languages are based on the use of "functions", whereas CPUs - the targets of programming languages - do no directly implement "functions" (you have to add code to subroutines to make functions)
- user-defined types
	- machines have only a few types
		- e.g. "bit" and "pointer to bit" (optimized to group bits into "bytes")
	- user-defined types allow new ways to invent a layer new types composed of machine types onto problems, which leads to complicated type checking algorithms
- using "functions" to describe asynchronous operations and parts
	- asynchronous parts are asynchronous, whereas "functions" imply synchrony (function calls are synchronous, caller blocks and waits for an answer from callee)

simplicity isn' just one thing. simplicity is in the eyes of the beholder

If you're an accountant, then spreadsheets are simple, OTOH, if you're trying to analyze self consistency and correctness of programs, then spreadsheets aren't sufficient nor very simple - they require you to add nuance (complexity) to handle deep edge cases.

If you're trying to invent new software systems, then Garbage Collection is a boon, since it lets you avoid low-level details of memory management, and deep type checking gets in the way of design. OTOH if you are trying to Production Engineer a software product by attempting to dot all the i's and cross all the T's, and are trying to squeeze "efficiency" out of the design, then the opposite is true - you want to get rid of generalized Garbage collection and replace it with project-specific memory management, and you want as much thorough type checking as possible to catch all of the edge cases in the software. A language that makes thorough, deep type checking easier is considered "simple". A language that allows you to manipulate memory excruciating detail yet checks that all memory management operations are self-consistent and safe makes the job of Production Engineering simpler.
