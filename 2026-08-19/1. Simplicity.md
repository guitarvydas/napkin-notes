# What Is Simplicity?
"lack of nuance"
# Examples of Simplicity
- UNIX
	- normalizes all APIs to devices, files, etc. to be one normalized kind - "files" and file descriptors
- Forth Haiku
	- small, simple notation maps to complicated GLSL code (approx. 2 lines to 100 lines)
- Forth
- Lisp 1.5
- Jos'h's command line arg parser, using arg reversal
- BNF as a way of specifying string matching (and eBNF, etc.)
- CPU opcodes instead of rats' nests of electronics
- Feynman diagrams
	- instead of just more functional equations
- K&R C vs. ANSI C
	- K&R C defines all routines to be "functions"
	- K&RC invented a simple type-checking model that covered a lot of cases, but not all cases - it was "just enough" to build systems software
- Prolog and relational programming
	- allows more concise expression of relationships, at cost of run-time speed (needs more CPU cycles)
- childrens' LEGO blocks
	- only one type for interconnection of blocks - a round peg of fixed dimensions
	- no tight coupling between blocks
	- blocks are interchangeable
- multi-stage computation
	- each stage does one thing and does it well
	- allows programmers to concentrate on only one thing at a time (leading to deeper solutions instead of wasting time on workarounds)
# Examples of Anti-Simplicity
- overuse of the functional paradigm
	- forcing all problems to fit one model - causes workarounds and unnecessary nuance when fitting a problem to the single model
	- the strive to use CPUs to automate mathematics has leaked, heavily, into programming practice, e.g. most programming languages are based on the use of "functions", whereas CPUs - the targets of programming languages - do no directly implement "functions" (you have to add code to subroutines to make functions)
- user-defined types
	- machines have only a few types
		- e.g. "bit" and "pointer to bit" (optimized to group bits into "bytes")
	- user-defined types allow new ways to invent a layer new types composed of machine types onto problems, which leads to complicated type checking algorithms
- using "functions" to describe asynchronous operations and parts
	- asynchronous parts are asynchronous, whereas "functions" imply synchrony (function calls are synchronous, caller blocks and waits for an answer from callee)

If you're an accountant, then spreadsheets are simple, OTOH, if you're trying to analyze self consistency and correctness of programs, then spreadsheets aren't sufficient nor very simple - they require you to add nuance (complexity) to handle deep edge cases.

OTOH if you are trying to Production Engineer a software product by attempting to dot all the i's and cross all the T's, and are trying to squeeze "efficiency" out of the design, then the opposite is true - you want to get rid of generalized Garbage collection and replace it with project-specific memory management, and you want as much thorough type checking as possible to catch all of the edge cases in the software. A language that makes thorough, deep type checking easier is considered "simple". A language that allows you to manipulate memory excruciating detail yet checks that all memory management operations are self-consistent and safe makes the job of Production Engineering simpler.

The article is mostly OK, but I want to add a few points:

Anti-Simplicity - BNF

BNF was almost immediately employed to create only niggly, bottom-up, over-burdened parser state machines which are "simple" only for building production quality parsers. This myopic view of BNF misses important other uses for the notation, like specifying string matchers for programming tool development, e.g. matching recursive text structures in ways that go beyond what REGEX can easily do. PEG (OhmJS) finally formalized recursive descent - top down, instead of bottom up - parsing, but, continues to be seen only as competition for production parser generators instead of as a way to open doors to new vistas in program development.

Anti-Simplicity - Operating Systems

If you step far enough back, you can see that the very concept of an operating system is not needed at all. A "proof" can be seen in early gaming systems, which didn't need all of the complicated, brittle fluff associated with modern operating systems. We intended to "simplify" program development by supplying common libraries of code in order to speed up program development. Instead of building these libraries like decoupled LEGO blocks, we stuck to the functional paradigm and created a huge ball of overly-coupled functionality which ships to every user and gets cherry picked at runtime. Instead of production engineering applications, we kept on adding nuances and complications to the libraries hoping to solve every production engineering problem. Instead of accepting the fact that the functional paradigm is unsuited to expressing asynchronous operation and composition of programs, we kept adding nuance to operating systems and libraries, essentially getting closer to, but never reaching, the asymptote.

Operating systems make software _development_ simpler but shouldn't be shipped, whole-hog to end users. Operating systems are just complicated, megabyte and gigabyte replacements for much simpler-to-use hardware rotary switches and game cartridges.

GPUs are just one production-engineering approach to providing a lump of code for each pixel on a screen. Would it be "simpler" (hardware and software) to just provide one small CPU - with private memory - per pixel?
