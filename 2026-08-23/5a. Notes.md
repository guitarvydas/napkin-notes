Calcifying our first guess into overly-detailed data structures and hard-coded code and too much type checking makes it harder to backtrack and to fit the design to the actual problem.

> During FDD you don't yet know what your AST should look like...

I view an AST as a DSL for string matching. Using an AST makes it easy to change the string matcher after you discover something. Using something like T2T (text-to-text based on the use of OhmJS to pattern match and on RWR to rewrite the match) makes it easy to backtrack. 

One technique in FDD is to write code that writes code. Instead of hard-coding your early ideas as code, you use little DSLs to create code for your early ideas. When your early ideas change, all you have to do is to tweak the source code in the DSLs and regenrate, instead of tweaking a humungous amount of already-hard-coded code that was manually written.

> Text is the loosest representation available. 

It's not so much that text is a loose representation (it is, and using something like T2T pulls structured information out of the text), but, that text is "what we've got" - we have lots of textual programming languages and code editors. Instead of inventing something new, it becomes easy to use "what we have" by writing code that writes code in whatever way is easiest.

ASTs and DSLs (like BNF, OhmJS grammars, etc.) make it easy to enact big changes with small amounts of edits (then use the machine to grind through and regenerate all of the code again).

Strings are very common. String manipulation libraries are very common. So, it behooves us to use what we've got and build strings that become programs.
