# Simulated Homoiconicity

**TL;DR** Homoiconicity means a language's code is represented in the same data structures the language already manipulates — Lisp's lists, Janet's lists and symbols. Most languages don't have that natively, but nearly all of them expose their compiler as a callable: hand it a string, get back executable code. That's simulated homoiconicity, and it is not a consolation prize for languages that lack the real thing. It is the right tool for the first, most neglected phase of programming — exploring a domain before you know its shape. The technique underneath is write code that writes code: instead of hand-coding a first guess about the domain directly, write a small DSL that generates the code, so that when the guess turns out wrong, you edit the DSL and regenerate instead of hand-editing everything you already built. Text is the medium for this not because it's structureless — pattern-matching tools like grammars pull plenty of structure out of it — but because it's what we already have: mature languages, editors, and string libraries, ready to be pointed at whatever DSL you invent this week.

---

## L;R

### What homoiconicity actually buys you

A Lisp expression like `(+ x (* y 2))` is not translated into some other representation before the language can work with it. It already is the representation — a list, whose first element is `+`, whose third element is another list. A macro that rewrites code is just a function that takes a list and returns a list. There is no separate AST format to learn, no serialization step standing between "the program I'm generating" and "the program that runs." `eval` closes the loop: hand it a list, get back a value.

Janet inherits this directly. `(+ 2 (* x 3))` is Janet data before it is anything else. Common Lisp, Scheme, and Clojure make the same deal.

### The simulated version: hand the compiler a string instead

Lua's parser turns `x + y * 2` into bytecode, not into a table you can inspect and rewrite. There's no native code-as-data story. But Lua has `load()`:

```lua
source = "return function(x) return x * 2 end"
f = load(source)()
```

`load` compiles a string into a callable function, at runtime, with no external process. Design your own AST as an ordinary Lua table, write a function that turns that table into Lua source text, and pipe the result through `load()`. From the outside it behaves like homoiconic metaprogramming. From the inside, there's a text-serialization step real homoiconicity doesn't need — but that step is not a defect. It's the whole reason the technique is useful, which is the point this piece wants to make.

This is close to the default across scripting languages, which is worth seeing laid out rather than taken on faith:

| Language | Code is native data? | Generate-and-run |
|---|---|---|
| Lisp / Scheme / Clojure | Yes | `eval` on data |
| Janet | Yes | `eval` on data |
| Rebol | Yes (blocks) | `do` on data or text |
| Julia | Partially (`Expr` objects) | `Meta.parse` + `eval` |
| Forth | Dictionary words, not data structures | `evaluate` on text |
| Lua | No | `load()` on text |
| Python | No | `compile()` + `exec`/`eval` |
| JavaScript | No | `Function()` / `eval` |
| Smalltalk (Squeak, Pharo, GST) | No (but reflective: `CompiledMethod` is a first-class object) | `evaluate:` on text |
| Ruby, Perl, Tcl, R, Elixir | No | `eval` on text |

The "yes" column is short. The "generate-and-run" column has an entry for every language on the list. That's the point of this table: simulated homoiconicity is not a fallback available to a handful of unlucky languages. It's close to universal, which means FDD-style exploration is available almost everywhere, whether or not the host language was ever designed with code-as-data in mind.

Julia's `Meta.parse` sits in between the two columns — it parses text into a structured `Expr` object rather than a raw string, so it's simulated homoiconicity with a shorter round-trip. Forth's `evaluate` is the same idea with no data-structure step at all: text goes in, dictionary entries come out. Rebol earns its "Yes" the way Lisp does: its native syntax is the block, a first-class data type that holds words and values the same way a Lisp list holds symbols and values, and `do` will evaluate either a block you built by hand or a string you built at runtime — real and simulated homoiconicity as two entry points into the same function.

Smalltalk belongs in the "No" camp by the same test Lua fails: `3 + 4` is not a Smalltalk object you can inspect and rewrite before it's compiled. But Smalltalk earns the parenthetical, because almost everything else about it is reflective in a way Lua isn't. A compiled method is an ordinary object (`CompiledMethod`), inspectable and decompilable at runtime. Classes are objects. The compiler is an object. And that compiler exposes exactly the entry point this piece keeps finding in every other language: `Behavior>>evaluate:` takes a string, compiles it, and runs it — which is also, not coincidentally, the mechanism behind every Smalltalk workspace "doit" since Smalltalk-80. Squeak and Pharo expose the same idea as `Compiler evaluate: '3 + 4'`.

### Two halves of the problem

Most of the discipline built around programming addresses one half of it: does the code do what the code says it does. Type systems, compilers, test suites, and formal methods all answer that question, and they answer it well. None of them answer the other half: is the code trying to do the right thing in the first place. Proving code correct does not prove the design is correct.

The only way to answer the second question is to find out you were wrong — build something, run it into the domain, discover what you didn't know, and rebuild with that knowledge. Failure is how you learn the shape of a problem you don't yet understand. Call this phase what it is: Failure Driven Development. It comes before Production Engineering, not after it, and most of the field's tooling is built for the phase that comes second.

### Write code that writes code

The core FDD technique is not "use text" — it's write code that writes code. When you have a first guess about a domain, the mistake is coding that guess directly: a function per idea, a class per concept, hard-coded and hand-written. The guess is provisional, but the code doesn't know that. When the guess changes — and during FDD it will, repeatedly — you're left manually editing a large pile of code you wrote by hand, one occurrence at a time.

Write a small DSL instead, and generate the code from it. When the guess changes, you change the DSL — usually a handful of lines — and regenerate everything downstream. The machine does the grinding; you do the editing, and only in one small place.

An AST fits into this as a DSL for string matching, not as its opposite. An AST is what you get when a grammar has pattern-matched your text into structure. The leverage isn't that the AST is loose — it's that a small edit to the grammar (a BNF rule, an OhmJS pattern) can regenerate a large amount of downstream code in one pass. T2T names a specific version of this pipeline: OhmJS does the pattern matching, RWR does the rewriting of what OhmJS matched, and the output is text again — ready for whatever `load()`-shaped pipeline picks it up next. Because the matcher and the rewrite rules are small and separate from each other, either one can be thrown away and rebuilt without touching the other.

### Text is what we've got

None of this makes text special because text is unstructured — T2T's whole job is pulling structure back out of it. Text earns its place for a more practical reason: it's already here. Decades of programming languages, editors, diffing tools, version control, and string-manipulation libraries are all built to work on text. Inventing a new structured interchange format means rebuilding all of that tooling for the new format. Generating text and handing it to an existing language's compiler means none of that has to be rebuilt — you get to reuse the biggest, best-tested toolchain available, which is the one every mainstream language already ships.

That's the actual trade a generate-source-and-`load()` pipeline is making. It isn't betting on looseness. It's betting that reusing what already exists — a parser someone else maintains, a compiler someone else optimized, an editor with syntax highlighting already built in — beats inventing a bespoke structured format before you know what that format needs to hold. Building the code twice, once to learn what the domain wants and once to keep, is cheaper than building it once against infrastructure you had to invent first.

### The mish-mosh method

This is why a pile of small, loosely-connected tools tends to outperform one comprehensive framework during exploration. `/bin/sh` scripts that shell out between languages, each bringing its own simplifying assumptions — relational thinking where the problem is relational, procedural code where it isn't — cost nothing to rewire when a piece turns out to be wrong, because nothing about the pipeline demanded a shared format up front.

Draw a decision tree, transmogrify it into Python. Draw a state diagram, transmogrify it into Python. Neither of those needs a compiler, a hand-built grammar, or a type system standing behind it before you can try it — just a small, disposable text generator and a language willing to `load()` or `exec()` the result. That's Diagrams as Syntax done the write-code-that-writes-code way, and it stays cheap precisely because nothing about it is built to last.

It also works with diagrams you didn't build a tool for. Most off-the-shelf diagram editors save out as a large lump of parseable text — XML, GraphML, whatever the tool's native format happens to be. It doesn't matter how ugly that export is. If a machine can parse it, [OhmJS](https://ohmjs.org) can pattern-match it, and once it's matched, RWR can rewrite it into source for any of the languages in the table above, as in [earlier experiments with text-to-text transpilation](https://programmingsimplicity.substack.com/p/experiments-with-text-to-text-transpilation?r=1egdky). You don't need to build a diagram editor to start building a diagrammatic language. You need a parser for whatever ugly text format an existing one already produces.

### When real homoiconicity earns its keep

None of this makes real homoiconicity worse — it makes it a different tool for a different moment. Once a design has converged, once you've thrown enough attempts at the domain to know the actual shape of the language you're building, the text-serialization step stops paying for itself. That's when Janet's version of the pipeline is worth the switch: your AST is already structured data, so macros and the compiler can operate on it directly, with no string round-trip and no reparse.

```
your syntax
     ↓
Janet PEG
     ↓
Janet data structures  ──→ transform ──→ macro ──→ compiler ──→ executable
```

That's a Production Engineering move. It's the right one after the design is settled, and the wrong one before it, for the same reason a type system is the right tool after you know your data's shape and the wrong tool for finding out what that shape should be.

### The name matters

Calling the `load()`-and-generate-text technique "fake" homoiconicity frames it as a lesser copy of the real thing, worth reaching for only when the real thing isn't available. That framing is backwards. It's a distinct technique with its own advantage — a representation with no schema, and therefore nothing to protect once you learn you were wrong. It deserves to be reached for on purpose, during the phase of a project where the actual work is finding out what you don't yet know, not treated as a workaround for languages that didn't do you the favor of being Lisp.

### Hello world, x + y = ???

Same trick, every row of the table. Build `x + y` as text (or, where the language allows it, as data), hand it to the language's own compiler at runtime, run it on `3` and `4`, and get `7` back. The ceremony differs; the shape underneath is identical everywhere: source in, callable out.

**Scheme (Guile) — data, not text**
```scheme
(define expr (list '+ 3 4))
(display (eval expr (interaction-environment)))
```

**Common Lisp (SBCL)**
```lisp
(defvar expr (list '+ 3 4))
(print (eval expr))
```

**Clojure**
```clojure
(def expr (list '+ 3 4))
(println (eval expr))
```

**Janet**
```janet
(def expr '(+ 3 4))
(print (eval expr))
```

**Rebol — blocks are native data, the way Lisp lists are**
```rebol
code: [3 + 4]
print do code
```

**Julia**
```julia
ex = Meta.parse("3 + 4")
println(eval(ex))
```

**Forth**
```forth
s" : addxy 3 4 + ;" evaluate
addxy .
```

**Lua**
```lua
source = "return function(x, y) return x + y end"
f = load(source)()
print(f(3, 4))
```

**Python**
```python
source = "def add(x, y): return x + y"
ns = {}
exec(source, ns)
print(ns["add"](3, 4))
```

**JavaScript**
```javascript
let f = new Function("x", "y", "return x + y");
console.log(f(3, 4));
```

**Ruby**
```ruby
source = "def add(x, y) x + y end"
eval(source)
puts add(3, 4)
```

**Perl**
```perl
my $source = 'sub add { return $_[0] + $_[1] }';
eval $source;
print add(3, 4), "\n";
```

**Tcl**
```tcl
set source {proc add {x y} {return [expr {$x + $y}]}}
eval $source
puts [add 3 4]
```

**R**
```r
expr <- parse(text = "3 + 4")
print(eval(expr))
```

**Smalltalk (GNU Smalltalk)**
```smalltalk
| result |
result := Object evaluate: '3 + 4'.
Transcript showCr: result printString.
```

**Smalltalk (Squeak, Pharo — same idiom, different spelling)**
```smalltalk
Transcript showCr: (Compiler evaluate: '3 + 4') printString.
```

**Elixir**
```elixir
{result, _} = Code.eval_string("3 + 4")
IO.puts(result)
```

Seventeen snippets, one pipeline. Every one of them ran, unmodified, as shown, except two.[^1] Scheme, Common Lisp, Clojure, and Janet skip the string entirely and hand `eval` a native list. Everyone else builds a string and hands it to something that compiles strings. Neither approach is the trick; the trick is noticing that "generate a program, then run it" is available almost everywhere, on demand, without waiting for a language that was designed for it.

[^1]: Rebol has no package-manager distribution, so that snippet follows documented block/`do` semantics rather than a test result. The Squeak/Pharo line is the identical `Compiler evaluate:` idiom the GNU Smalltalk snippet above it already verified — but the downloaded Squeak image is a full desktop app that opens a first-boot welcome wizard on startup and hangs waiting for GUI input even under `-headless`, so it wasn't run to completion in this sandbox. GNU Smalltalk (`gst`) has no such wizard; that one ran clean.
