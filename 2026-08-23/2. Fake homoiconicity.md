> is Lua homoiconic? If not, can it fake homoiconicity by writing a text file, shelling-out to compile it, then load the result at runtime?
> 

No. **Lua is not homoiconic**, at least not in the usual Lisp/Scheme sense.

The distinction is important because Lua _does_ make it quite easy to manipulate and generate code dynamically.

### What homoiconicity means

In a homoiconic language such as Lisp, the program:

```lisp
(+ x (* y 2))
```

is naturally represented as a Lisp data structure:

```lisp
(+ x (* y 2))
```

Conceptually:

```text
list
 ├── +
 ├── x
 └── list
      ├── *
      ├── y
      └── 2
```

The representation of **code is itself ordinary language data**. That's what makes Lisp macros so powerful.

Lua doesn't work that way. Lua source such as:

```lua
x + y * 2
```

is not a Lua table that you can simply inspect and modify. Lua's parser turns it into bytecode/function objects. Lua tables can certainly **represent** an AST, but that's a representation you have designed yourself, not Lua's native representation of code.

### But your idea absolutely works

In fact, Lua has unusually good facilities for doing what you're proposing.

You can construct Lua source code as a string:

```lua
source = [[
    return function(x)
        return x * 2
    end
]]
```

and then:

```lua
f = load(source)()
print(f(10))
```

`load` compiles the source string into a Lua function at runtime. The official Lua manual explicitly defines `load` this way: it takes a string containing a chunk, compiles it, and returns the resulting function. ([Lua](https://www.lua.org/manual/5.4/manual.html?external_link=true&utm_source=chatgpt.com "Lua 5.4 Reference Manual"))

So you **don't even need to write a file or shell out to the compiler**.

You could do:

```lua
source = generate_some_lua_code()
f = assert(load(source))()
```

This is essentially **runtime metaprogramming**.

### You could go one step further

Suppose you invent an AST representation using Lua tables:

```lua
ast = {
    "add",
    {"multiply", "x", 2},
    "y"
}
```

Then write a compiler:

```lua
function compile(ast)
    -- turn AST into Lua source
end
```

and:

```lua
source = compile(ast)
f = assert(load(source))()
```

You now have something that **feels quite a lot like homoiconic programming**, even though Lua itself isn't homoiconic.

The architecture would be:

```text
             Lua tables
                 │
                 │ AST
                 ▼
          your code generator
                 │
                 │ Lua source
                 ▼
              load()
                 │
                 │ compiled Lua
                 ▼
              function
```

### And your "write a file, compile, load" idea works too

You could do:

```text
Lua program
    │
    ├── generate foo.lua
    │
    ├── invoke luac
    │
    └── load foo.luac
```

Lua explicitly supports precompiled binary chunks. The language manual says that source and compiled forms are interchangeable, and `load`/`loadfile` can load either. ([Lua](https://www.lua.org/manual/5.4/manual.html?external_link=true&utm_source=chatgpt.com "Lua 5.4 Reference Manual"))

But that's unnecessarily cumbersome for most purposes. **`load()` gives you the compiler as part of the runtime.**

### The interesting distinction

I would characterize Lua as:

> **Not homoiconic, but highly amenable to metaprogramming.**

And there's an interesting connection to your earlier questions about Forth and Lisp.

|Language|Code as ordinary data?|Runtime code generation|
|---|---|---|
|Lisp/Scheme|**Yes**|Yes|
|Forth|Very strong code/data relationship|Yes|
|Lua|**No**|**Yes**|
|Python|No|Yes (`eval`/`exec`)|
|JavaScript|No|Yes (`eval`, `Function`)|

Lua's `load()` is particularly interesting because **compilation is explicitly exposed as a normal runtime operation**. Lua's own documentation describes the Lua compiler as being part of the runtime environment; `loadfile`, for example, compiles a chunk without executing it and returns the resulting function. ([Lua](https://www.lua.org/pil/8.html?utm_source=chatgpt.com "Programming in Lua : 8"))

So if what you're really interested in is **"can I use Lua as a substrate for a homoiconic/diagrammatic/metaprogramming language?"**, the answer is **yes, quite easily**. You'd probably want to represent your language's AST as Lua tables and generate Lua source (or directly generate Lua bytecode, though that's much more difficult).

And that gives you an interesting three-level system:

```text
your language's AST
        ↓
    Lua source
        ↓
   Lua compiler
        ↓
   Lua bytecode
        ↓
     execution
```

That is not homoiconicity **in Lua**, but it can give your _language built on Lua_ essentially the same practical metaprogramming capability.

> what other languages can use this load trick?

Quite a few. If by the **“Lua `load` trick”** you mean:

> construct source code as a string at runtime → invoke the language's compiler/interpreter on that string → get executable code back,

then this is a surprisingly common capability.

### Closest equivalents

|Language|Mechanism|What you get back|
|---|---|---|
|**Lua**|`load(string)`|function|
|**Python**|`eval(string)` / `exec(string)`|value / executed code|
|**JavaScript**|`eval(string)` / `Function(string)`|value / function|
|**Ruby**|`eval(string)`|value / executable code|
|**Perl**|`eval STRING`|value / executed code|
|**Tcl**|`eval string`|result|
|**R**|`parse()` + `eval()`|expression / result|
|**Julia**|`Meta.parse()` + `eval()`|expression / result|
|**Elixir**|`Code.eval_string()`|result + bindings|
|**Clojure**|`read-string` + `eval`|value|
|**Common Lisp**|`read-from-string` + `eval`|value|
|**Scheme**|`eval`|value|
|**Forth**|`evaluate` / interpreter mechanisms|compiled/interpreted words|
|**Smalltalk**|compiler/evaluation APIs|executable objects|

But there are some **important differences**.

### Lua is unusually clean

Lua's:

```lua
f = load("return function(x) return x * 2 end")()
```

is particularly nice because `load()` effectively gives you:

```text
source text → compiled chunk → function
```

So you can write a little compiler that emits Lua:

```lua
source = compile(my_ast)
fn = assert(load(source))()
```

and the result is a normal Lua function.

### Python

Python has the same basic capability, although the interface is split:

```python
code = compile(source, "<generated>", "exec")
exec(code)
```

or:

```python
code = compile(source, "<generated>", "eval")
result = eval(code)
```

This is actually quite powerful because you can separate **compilation** from **execution**.

You can therefore do:

```text
AST
 ↓
generate Python source
 ↓
compile()
 ↓
code object
 ↓
exec()
```

### JavaScript

JavaScript is similar:

```javascript
let f = new Function("x", "return x * 2");
console.log(f(10));
```

or:

```javascript
eval(source);
```

`Function()` is arguably closer to Lua's `load()` because you can generate a function directly.

### Common Lisp is a different beast

This is where it gets particularly interesting given your question about **homoiconicity**.

In Common Lisp:

```lisp
(eval '(+ 2 3))
```

works because:

```lisp
'(+ 2 3)
```

is ordinary Lisp data representing a Lisp expression.

And you can construct that data:

```lisp
(eval (list '+ 2 3))
```

So instead of:

```text
AST → source text → compiler
```

you can have:

```text
Lisp data/AST → eval
```

That's the **homoiconic advantage**.

### Julia is also interesting

Julia exposes its syntax tree:

```julia
ex = Meta.parse("x + 2")
eval(ex)
```

So Julia gives you something closer to Lisp:

```text
source
  ↓
Meta.parse
  ↓
Expr object
  ↓
eval
```

`Expr` is a first-class representation of Julia expressions.

### Forth is another interesting case

Forth has an even more intimate relationship between the language and its compiler/interpreter.

You can feed text to the interpreter:

```forth
s" : double dup + ;" evaluate
```

and you've effectively generated new Forth code and compiled it into the dictionary.

That makes Forth, Lisp and Lua interesting points on a spectrum:

```text
        code/data relationship
              ↑
              │
 Lisp ────────┤  code is data
 Forth ───────┤  words are dictionary objects
 Julia ───────┤  Expr objects
 Lua ─────────┤  source → load()
 Python ──────┤  source → compile()
 JavaScript ──┤  source → eval()
              │
              ↓
```

### If your real interest is building another language

Then I'd pay particular attention to **Lua, Lisp, Julia and Forth**.

They give you four quite different implementation strategies:

**Lisp**

```text
your AST = Lisp data
       ↓
      eval
```

**Julia**

```text
your AST
   ↓
Julia Expr
   ↓
eval
```

**Lua**

```text
your AST
   ↓
Lua source
   ↓
load()
```

**Forth**

```text
your language
   ↓
Forth source
   ↓
EVALUATE
   ↓
Forth dictionary
```

For something like your **0D/diagrammatic programming work**, the Lua approach is particularly attractive: **your diagrams can be the source language, you generate Lua text, and `load()` turns the generated program into executable Lua without requiring an external compiler process.**
