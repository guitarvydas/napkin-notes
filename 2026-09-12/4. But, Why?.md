---

This is really the crux of the whole exercise, and it deserves more than an assertion — let me actually demonstrate it rather than just claim it, since that's been the standard for everything else in this conversation.

The short answer: it _is_ optimized away, exactly when the compiler can prove it's safe to. The overhead you measured earlier is specifically the cost of values the compiler **can't** prove are safe to strip — and that's most values, for reasons baked into what these languages promise. Let me show both halves of that.Line 7 (`useLocally`, string built and discarded within the function): **"does not escape."** Line 15 (`forceEscape`, string stored into a package-level variable): **"escapes to heap."** The Go compiler is telling us directly: when it can _prove_ a value never needs to outlive its stack frame, it emits zero header and zero heap allocation — genuinely C-level cost. The moment the value needs to be read later by code the compiler can't fully see through, the header comes back.

Now let's check whether this happens even in a language people assume is _always_ boxed — via the JVM's JIT, which does this speculatively at runtime rather than provably at compile time.Interesting — no difference. Let's check whether HotSpot's C2 compiler actually applied escape analysis here, using its diagnostic output rather than guessing.A clean, simple object gets **true zero-byte allocation** via escape analysis — real proof the JIT can reach C-level cost dynamically. But `String`'s constructor didn't get the same treatment. Let's check if that's an inlining-budget limitation, which would be a genuinely instructive finding.Both experiments landed cleanly, and together they answer the question better than a paragraph could.

**Go proves it ahead of time.** The compiler's own diagnostic said it: the string in `useLocally` — built, read, discarded, never stored — **"does not escape."** It costs nothing beyond a stack slot: no header, no heap allocation, genuinely C-level. The string in `forceEscape` — stored into a package variable — **"escapes to heap"** and pays the full cost. This isn't a hypothetical; it's what the compiler unconditionally does, for every allocation, at every build.

**The JVM proves it speculatively, at runtime — and it actually works, some of the time.** A plain two-field `Point` object, allocated in a hot loop and never stored anywhere: **0.000 bytes/call.** Not "small" — literally zero. HotSpot's C2 JIT proved the object never escapes, decomposed it into its two `int` fields (scalar replacement), and never materialized it on the heap at all. The escaping version paid the expected 24 bytes. This is the same trick as Go's, just discovered by profiling instead of by static proof.

But then `String` — same idea, same non-escaping use — didn't get the treatment: 72 bytes/call, identical whether it escaped or not. I tried loosening the JIT's inlining budget substantially in case the constructor was just too big to see through; it made no difference. `String`'s constructor apparently has something in it (internal array allocation, `System.arraycopy`, coder/charset branching) that defeats this specific optimizer's escape proof, even though nothing semantic prevents it — the JVM's answer to "can you avoid this" is "yes, sometimes, when the implementation's analysis happens to reach far enough," which is a real and honestly not-fully-satisfying answer.

**So the picture is:**

The optimization you're describing isn't missing — it's real, it's implemented, and it can get you to true zero overhead. What it needs is _proof_, and there are two entirely different reasons proof is often unavailable:

1. **The language itself promises things that require the metadata to exist for someone.** A dynamically-typed language needs a uniform box for "value of unknown type" precisely so `x = 5; x = "hi"` can share a slot — that's not sloppiness, it's the feature. Reflection, `id()`/identity comparison, `hash()` caching across arbitrary future uses, monkey-patching, `eval` — every one of these means a compiler can't prove "nobody will ever need this string's identity or hash" without essentially running the whole program first, including code it hasn't loaded yet. Go and Rust don't have this problem because they never made that promise: no runtime reflection into layout, no redefinition of running code, ownership resolved once at compile time. They aren't optimizing the cost away — they never incurred it, because the language closed off the dynamism that would have required it.
    
2. **Even where proof is possible, an optimizer's reach is bounded by engineering budget, not just theory.** The `Point`-vs-`String` result above is exactly this: identical _provability_ in principle, wildly different outcome in practice, because scalar replacement's implementation has limits (inlining depth, array handling, code complexity) that a two-field object clears and a stdlib constructor doesn't. This is why "the JIT will handle it" is true in benchmarks and unreliable in real programs — it depends on whether your specific allocation pattern happens to fall inside the optimizer's actual coverage, which is much narrower than its theoretical scope.
    

CPython adds a third, non-technical reason worth naming: even optimizations that **are** provably safe can be politically/practically off the table. NumPy and the entire C-extension ecosystem read `PyObject` layout directly through the stable/unstable C API — CPython can't change string representation or drop the header for any string that might cross that boundary without breaking the ecosystem, regardless of what any analysis proves. (This is precisely why Faster CPython's recent work — the specializing adaptive interpreter, the 3.13+ experimental JIT — works _around_ the layout rather than changing it.)

So the honest framing of your original question: the overhead isn't unoptimized, it's _unprovable-or-uneconomical-to-prove-away_, and that's a direct, mechanical consequence of what the language chose to promise its programmers. Cost gets paid at compile time (Rust's borrow checker, Go's escape analysis — restrict the language, prove more, pay less) or at run time (Python/JVM/JS — keep the language open, pay per-value) — nobody has found a way to keep full dynamism _and_ pay nothing, because that would mean proving a property of an arbitrary program without running it.

Your pool sidesteps the whole dilemma rather than solving it: by committing at design time to "every entry is always a UTF-8 byte span, never anything polymorphic," you get the proof for free from the type itself, the same way Go's compiler gets it from static analysis — you just did it by hand, once, instead of asking an optimizer to rediscover it every time.
