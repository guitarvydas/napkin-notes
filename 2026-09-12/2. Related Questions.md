## Is the `"abc"` test reasonable, or does it exacerbate an edge case?

Both, depending on which cost you're looking at — and the chart above separates the two cleanly.

For the **additive-header** designs (CPython, JVM/Clojure, V8, SBCL, Racket, PHP, C++'s pre-SSO-threshold case) — yes, 3 characters is close to the worst case. A fixed per-object header amortizes over content length, so testing at n=3 puts every one of these languages near its _local maximum_ overhead ratio. CPython's 14.7× at n=3 drops to 1.4× by n=100 and is indistinguishable from C by n=1000. The original table wasn't lying, but it was reporting the peak of a curve that falls fast.

But two of the entries are **not** additive-header designs, and for those, n=3 is perfectly representative, not exaggerated at all:

- **C#'s 2× (UTF-16)** is a fixed multiplicative tax on every ASCII character, forever. It doesn't shrink because it isn't a header — it's an encoding-width decision. A 10,000-character C# string still costs exactly 2 bytes per character.
- **Haskell's 40×** doesn't budge either, for a different reason: there's no header to amortize. Every single character re-pays the full cons-cell-plus-boxed-Char cost. It's not "high at small sizes," it's _linearly this bad at every size_ — arguably a real scaling liability, not a startup cost.

So the honest answer: the test slightly overstates how bad _header-carrying_ languages look in typical programs (most real strings — identifiers, JSON keys, words — are still short enough to feel some of this, but not the full peak), while it exactly represents the ongoing cost of the width- and structure-based designs, which never improve.

## Where's the knee?

There is one, and it's governed entirely by header-size-to-content ratio: overhead crosses below 1.5× once `n` reaches roughly **2–3× the header size**, and below 1.1× by roughly **10× the header size**. Concretely from the numbers above:

- Go/Odin/Zig (16-byte header): under 1.2× by n≈100
- CPython (41-byte header): under 1.15× by n≈300
- JVM (40-byte combined header): under 1.15× by n≈300

Real code sits in an interesting spot relative to this: identifiers, dict keys, and short labels are commonly 5–20 characters — well _before_ the knee for most of these languages. A typical JSON key or variable name is still paying 3–10× overhead in a boxed-string language. The knee is real, but it arrives later than casual intuition suggests; you need paragraph-length strings, not word-length ones, before the header stops mattering.

The genuinely important asymmetry the chart makes obvious: **additive costs amortize, multiplicative costs don't.** A header is a one-time toll; a width or structural choice is a per-mile toll. No amount of string length rescues Haskell's `String` or dilutes C#'s UTF-16 tax — which is exactly why real Haskell code uses `Text`/`ByteString` instead of the default, and why languages that need both ASCII-cheapness and Unicode correctness (Python's PEP 393, Java's compact strings) ended up building _adaptive_ width rather than committing to one.

## What led to encumbering strings this way?

Every piece of header weight traces back to a specific problem C's raw `char*` doesn't solve:

- **O(1) length, and safety.** `strlen` is O(n) and null-termination is a decades-long source of bugs (truncation on embedded NUL, buffer overruns, the class of vulnerability Heartbleed belongs to). Storing length explicitly costs a word; it buys correctness and speed for a compulsively common operation.
- **Hashing.** Strings are the dominant key type in every dynamic language's dict/map. Caching the hash (Python, Java, PHP, Ruby, Lua) trades 4–8 bytes for never recomputing a hash on a string you've already hashed once — a good bet when the same short strings (identifiers, keys) get hashed repeatedly.
- **GC bookkeeping.** This is the single biggest driver of "boxed object" weight. Any language with automatic memory management needs a type tag and mark/reachability bits on _every_ heap object, strings included — it's not a decision about strings specifically, it's the price of admission to that memory model. This is precisely why C, Go, Rust, Zig, and Odin — all either manually-managed or ownership-tracked rather than traced — get away with near-zero header weight: nothing needs to trace them.
- **Unicode.** Once you support more than ASCII you must pick: tag the width per-string and adapt (Python's PEP 393, Java's Latin-1/UTF-16 split), commit to one fixed wide representation always (SBCL, Racket — simple, but pays 4 bytes/char even for pure ASCII), or keep UTF-8 as the one true representation and accept O(n) indexing by code point (Go, Rust, Swift). Every one of these costs _something_; there's no free option once the character set exceeds one byte.
- **Immutability and interning.** Safe sharing needs either GC (Python/Java/JS just let the collector handle lifetime) or refcounting (PHP, Lua) — both need a bookkeeping field.

Two of the outliers in the table have causes worth calling out specifically since they're not really about strings at all:

- **The JVM's two-object split (wrapper + backing array)** is a direct consequence of the object model, not a string-specific choice: Java has no flexible-array-member equivalent — an object can't end in "and then N more bytes inline" the way a C struct or JanetStringHead can — so any variable-length payload _must_ live in a separately-headed array object, referenced by pointer. Clojure inherits this for free by being a String, not by any deliberate design of its own.
- **Haskell's `String = [Char]`** isn't a performance decision at all — it's a consequence of the language's founding aesthetic: lists are the canonical data structure in a lazy, pure functional language, so making strings "just a list of characters" was the elegant, teachable, laziness-composable choice when the design was set. The performance cost was known and accepted for decades, which is exactly why `Data.Text` and `Data.ByteString` exist as the real-world answer — `String` stays the default for backward compatibility and pedagogy, not because anyone thinks 40 bytes/char is a good trade.

The throughline: systems languages treat "what does a string cost" as a question the programmer should answer explicitly, and everything above is _opt-in_ machinery that managed languages bought on the programmer's behalf, in exchange for not having to think about hashing, memory safety, or Unicode width by hand. Your pool sits deliberately outside both camps — it gets the O(1)-length and hashing benefits of a header without paying it per-string, by lifting the header into its own parallel array. That's essentially the JVM's split-object idea, but with the "array" being shared infrastructure instead of one object per string.
