# Why Notations?

2026-11-06

## Rhetorical questions

- Why bother with DSLs, why not just use the underlying PLs?
- Why bother with PLs, why not just use assembler?
- Why bother with assembler, why not just build electronics hardware using schematics?
- Why bother with electronics, why not just build using materials science?
- Why bother with materials science, why not just build using atoms?

## Answer:

Because simplifying notations make doing some specific things easier.

But, simplifying assumptions ignore certain classes of generalities, for example, assembler can only produce hardware that follows certain guidelines. The guidelines are determined by the opcodes provided by specific CPU architectures. Electronics is more general than programming, but, programming CPUs is easier and more accessible to many more people than is electronics design.

## Where to Focus?

We need to focus more on building DSLs and little notations, rather than elaborating and generalizing old-fashioned PLs and various tools, like type checking.

## Questions Regarding Moving Forward

SQL is a DSL. Is it easy to write? Is it easy to read? Is it easy to build?

REGEX is a DSL. Is it easy to write? Is it easy to read? Is it easy to build?

BNF is a DSL. Is it easy to write? Is it easy to read? Is it easy to build?

Lisp macros are DSLs. Are they easy to write? Are they easy to read? Are they easy to build?

Racket Language Oriented Programming produces DSLs. Are the DSLs easy to write? Are they easy to read? Are they easy to build?

PEG libraries for various languages create DSLs. Are they easy to write? Are they easy to read? Are they easy to build?

PEG embedded into various languages helps to create DSLs, e.g. Rebol, Janet. Are these DSLs easy to write? Are they easy to read? Are they easy to build?

What's easier than SQL, REGEX, etc? I claim that SCNs - little, nano-DSLs - are a step in that direction. The goals are:

- to be able to build them quickly (approximately an hour or so)
- to allow syntactic freedom, so more people can read them more easily (that quality depends on the abilities of the SCN-creator to choose & design wisely)
- to customize DSLs/notations on a per-project basis, instead of generalizing them for use across many projects
- to allow using multiple DSLs/notations in each project. That seems to contradict the current prejudice against using multiple languages. Why does that prejudice exist? How can we turn it around?
- to allow portability between PLs (instead of allowing portability by extending PLs with features like `#ifdefs`)
- to allow using Diagrams as Syntax (DaS) instead of sticking only to 500-year old type-setting technology
- enable speed of development by removing complexity
- to use SCN-based tools to create new SCNs

Using PBP, DaS, T2T[^1] makes it possible to more-easily build notations disregarding the biased syntax of the target PLs. This isn't the full answer to the above set of problems, but I claim that it is a step in that direction. Essentially, writing an SCN[^2] in PBP or T2T is like writing a compiler, except that you can expect to be finished in an afternoon or so, instead of in several years. Take the complexity out, enable speed of development.

What contributes to complexity? Niggly details. Breaking data shapes down into various specific types. If you intend to analyze code, or believe that perfect code is necessary and actually achievable, then you need this level of complexity. If you just want to build useful devices, you don't this kind of complexity. You might need complexity that is related to the problem-at-hand, but you want to ignore complexities that are beyond the scope of the problem-at-hand. Proving that code is perfect involves different issues than making a useful device.

Analogy: you don't want to create Ford Pintos that explode into flames in accidents, but it must be noted that Mercedes builds cars that work without MB having yet attained design perfection.

[^1]:  T2T == text to text == PEG + text rewriting
[^2]: SCN == Solution Centric Notation == throw-away nano-DSL for use on a per-project basis
