*comparing T2T approach to Lisp and Ruby DSL approaches (Claude)*

Going by your `t2t` script and the RWR/Ohm material from your earlier article work, T2T sits on a third point that neither Ruby nor Lisp occupies. I'm working from the script, so correct me if I've mischaracterized the RWR side.

## What T2T is, in these terms

T2T takes an Ohm grammar (`.ohm`) and a rewrite spec (`.rwr`), compiles the spec to JS (`rwr.mjs`), splices grammar, support code, and rewrite rules into a generated node program, then runs that program on stdin. Each DSL gets its own small, throwaway transpiler: text in, text out.

That makes it an **external DSL toolchain with macro-like semantics**. Like a Lisp macro, it's source-to-source and runs before the target does. Like a Ruby DSL, it doesn't need homoiconicity. The difference is that it gets its power from a real parser rather than from the host language's syntax.

## Comparison

| | Ruby DSL | Lisp macro | T2T |
|---|---|---|---|
|**Kind**|Internal|Internal|External|
|**Syntax freedom**|Ruby's grammar only|S-expressions only|Anything a PEG can parse, including diagram-derived text|
|**When it acts**|Runtime|Macroexpansion time|A separate build stage|
|**Input representation**|Live objects, blocks|Code as lists|Plain text, parsed by Ohm|
|**Output**|Behavior in the running process|Code in the same language|Text in any target language|
|**Host coupling**|Total (must be Ruby)|Total (must be Lisp)|None: the target can be anything|
|**Composition**|Method calls and nesting|Macros expanding into macros|Unix-style pipeline of stages|
|**Error reporting**|Stack traces into metaprogramming|Expansion-time errors, often confusing|Grammar failures at parse time, but errors in generated output surface in the target|
|**Toolchain cost**|None|None|Real: build step, temp files, generated programs|

## Where T2T is stronger

- **No host-syntax tax.** Ruby DSLs have to look like Ruby, and Lisp DSLs have to look like parenthesized prefix forms. A T2T notation can look like whatever suits the domain, which is your "syntax is cheap" argument made operational.
- **Host independence.** A macro can only emit the language it lives in. T2T can emit Python, JS, Common Lisp, or anything else, so one notation can target several back ends.
- **Parsing is a first-class tool.** Lisp gets parsing for free by restricting syntax to S-expressions. T2T uses a proper grammar, so you get real error positions on malformed input rather than whatever the host reader allows.
- **Small, disposable languages.** Ruby and Lisp DSLs tend to accrete into a library. A per-problem nanoDSL stays small.

## Where it pays for that

- **Text-level output.** Lisp macros produce structured code, so the result is well-formed by construction. T2T emits text, which puts it closer to Ruby's `class_eval` with heredocs: unbalanced output or injected fragments won't be caught until the target compiler sees them.
- **No integration with the host compiler.** A macro can see the lexical environment, expand in context, and be optimized with the surrounding code. T2T stages are blind to each other and to the target's scope.
- **Errors surface one stage away.** When the generated code fails, you're reading output the user never wrote. Macros and Ruby DSLs share this problem, but a pipeline of generated programs makes it a bit worse.
- **Build and process overhead.** Ruby and Lisp DSLs cost nothing to adopt. T2T needs the pipeline, temp files, and process orchestration, which your EAGAIN debugging showed is not free.

## Where each fits

Lisp macros are the best fit when the DSL needs new semantics inside one language. Ruby DSLs fit when the DSL should be a friendly face on an object model. T2T fits when the notation itself is the point, especially when it's non-textual in origin, like diagrams, or when the output language isn't the one you're writing in.

One difference sits underneath all the others. In Ruby and Lisp the DSL author is constrained by the language and reaps convenience for it. In T2T you give up that convenience and gain the freedom to choose the notation, the target, and the stage boundaries. That's the "notation as a design variable" position, and neither Ruby nor Lisp can offer it without leaving the host language.
